# The first real corpus: `OwensLab/CommunityForensics-Eval`, tranche `commfor_eval_v1`

This document exists because T59's acceptance clause is not "produce a metrics table" but *"a number
that cannot be re-fetched from that document is not reported"*. It is the audit trail for the first
metrics this repository has ever printed from bytes that were generated by somebody else: what was
downloaded, from which URL and row offset, what arrived, what the harness refused to compute, and the
two artefacts (a manifest and a split assignment) that every later number here is tied to.

Nothing in it is a claim about SynthVerify's product. The corpus lives in `data/corpora/commfor/`,
which is in `.gitignore` — third-party research images are never committed, and the licence is
non-commercial. Every figure below was copied from a command's own stdout; the commands are at the end,
in the order they ran.

---

## 1. What the source serves

Queried live on 2026-09-29 against the Hugging Face Hub API and the Datasets Server:

| | `OwensLab/CommunityForensics-Small` | `OwensLab/CommunityForensics-Eval` |
|---|---|---|
| `gated` as served | `False` | `False` |
| licence as served | `cc-by-nc-sa-4.0` | `cc-by-nc-sa-4.0` |
| configs | `default` | `default` |
| columns served | `image_name, format, resolution, mode, image_data, model_name, nsfw_flag, prompt, real_source, subset, split, label, architecture` | identical |
| splits served | **`train`: 10,542 rows** | **`CompEval`: 51,836 rows** |

**The deviation this records.** The plan (TODO T59, and the Phase-2 decision at TODO:1700) named
`CommunityForensics-Small`. The tranche that was actually fetched comes from `CommunityForensics-Eval`,
and the reason is the last row of that table rather than a preference: **Small serves exactly one split
and it is called `train`.** Using it as an evaluation corpus would mean measuring a detector on rows
from the training distribution of the same set — the leak T58 closed at the reporting end, re-opened at
the data end, where no flag can see it. `CompEval` is the split the authors publish *for* evaluation,
and every row in this tranche carries `"split": "test"` and `"subset": "CompEval"` in its own source
metadata (measured: `Counter({'test': 2376})`, `Counter({'CompEval': 2376})`).

The authors' own contamination instruction, quoted from the dataset card rather than paraphrased:

> To avoid data contamination, please use the attached FFHQ train/test split if you intend to use this
> evaluation set. … Also, make sure to only train on the "train" split of the COCO dataset. … RAISE
> dataset should not be used during training.

That constrains **Phase 3**, where a detector is fitted. Nothing here trains — the five heuristics
score a file with no parameters learned from this corpus — so this tranche is a legitimate evaluation
set and an illegitimate training set, and the learned detector must be sourced elsewhere.

## 2. What was fetched, and from where

`scripts/commfor_fetch.py` is operator-side and deliberately wired into no `make` target, no CI job and
no test: FC-4 says the product never fetches, so the download is a step a human runs before the
measurement. It reads the Datasets Server row endpoint, whose only documented read path for a binary
column is base64 in JSON:

```
https://datasets-server.huggingface.co/rows?dataset=OwensLab%2FCommunityForensics-Eval
  &config=default&split=CompEval&offset=<row>&length=<1..50>&partial=false
```

**59 distinct URLs were used**, offsets from 0 to 45,420. Four plan files ran, in this order, because
the first read of the corpus exposed two cells whose blocks were not where the coarse survey suggested:

| pass | plan | wrote | why it exists |
|---|---|---|---|
| 1 | `scripts/commfor_plan_v1.json` | 1,836 | the designed tranche |
| 2 | `scripts/commfor_plan_v1b.json` | 340 | two cells came back short (below) |
| 3 | `scripts/commfor_plan_v1c.json` | 120 | top-up before the split was written |
| 4 | `scripts/commfor_plan_v1d.json` | 80 | one cell still on the `MIN_CELL_N` boundary |

Counters summed over the four passes' own JSON blocks, using the field names each pass actually
printed: **`written` 2,376 · `resumed` 0 · `skipped_label` 240 · `skipped_magic` 7 ·
`skipped_truncated` 0 · `gaps` 2 · `skipped_container` 0**. The 240 label skips are rows whose
`model_name`/`label` disagreed with the cell that asked for them. The 2 gaps were a `502` and a `500` at
offsets 45,100 and 45,150 on the first pass; the fetcher records a gap, moves past it and keeps going, so
a permanently failing row costs a disclosed hole rather than the run.

Those 7 `skipped_magic` counts are the one place where a reader has to hold the log and the code
side by side, so say plainly what they are: the LAION real pools contain `format: "WEBP"` rows and this
fetch keeps PNG and JPEG only. Pass 1 ran before the counter existed in its current shape, so its JSON
calls them `skipped_magic` and its per-row line reads `format 'WEBP' does not match its bytes` — which
blames the source for something that is a property of *this tool*. The code since split the counter into
`skipped_container` (a format this fetch does not accept; rows 25,016 / 25,047 / 36,027 / 36,074 /
36,122 / 43,012 / 43,102, all WEBP) and `skipped_magic` (bytes that genuinely disagree with the format
claimed), and no later pass reported a magic mismatch. All seven sit in the three LAION real cells
(`Dalle2`, `Firefly_Image3`, `MidjourneyV5_2` — the reals fetched in those same ranges all report
`real_source: "LAION"`), so the LAION real pool this tranche draws is smaller than CompEval's by those
7 rows and nothing else lost them. **Consequence: the local corpus is PNG-and-JPEG by
construction of the fetcher**, which is a selection effect the metrics have to be read against, not a
property of CompEval.

**The second deviation.** The plan's `require_real_separately` flag says the real class should come from
COCO val rather than from the reals sitting inside a generated corpus, because those may themselves be
generated. This tranche uses CompEval's own paired pools. It was a deliberate trade: a separately
fetched COCO val would have made *container* and *capture* differences between the classes a function of
two different pipelines instead of one, which is worse for the confound and costs a second licence and a
second download. The cost is honest and stated here: **the real class is the corpus's own reals, and no
claim in this document depends on them being independently authenticated.**

### What the two short passes found about the source's layout

Pass 1 asked for 14 cells — one per generator's fakes plus six paired real pools — off a stride-500
survey of the split: 104 offsets sampled, **84 usable, 20 returning permanent `500`s**, and the 84
read as 53 `(model_name, label)` transitions. Two cells landed short — DFGAN's paired reals at 3 of 120,
Hourglass's fakes at 33 of 220 — because the fetcher stops a range after 25 consecutive rows outside the
declared cell, and a stride-500 transition says where a block starts, not how it is made. A stride-25
locator over **17,600–20,100** (120 rows sampled) read what is actually there:

```
 18950  Hourglass                label=1 src=imagenet  PNG   [256, 256]
 19050  Hourglass                label=0 src=imagenet  JPEG  [500, 374]
 19150  Hourglass                label=1 src=imagenet  PNG   [256, 256]
 19750  Hourglass                label=1 src=imagenet  PNG   [256, 256]
 19775  IdeogramV1               label=0 src=LAION     JPEG  [475, 475]
```

A generator's block is not one run of fakes: its fakes and its paired reals sit in **alternating runs**
— 18,950 and 19,150 are the same label, 19,050 between them is the other — so a 90-row run of the wrong
label is normal and not the end of the block. Passes 2–4 therefore carry an explicit
`stop_after_misses` of 200 (120 for the last), and pass 3's DFGAN attempt at row 44,120 answered a
question the plan had assumed: that second DFGAN/coco block is reals only — 0 fakes in 150 rows — so the
continuation was fetched from row 620 instead, where the first block was still unspent. The survey says
the same thing from the other side: `Hourglass` appears as a block start at 10,000, 13,500, 19,000 and
34,000, so a generator's rows recur across the split rather than occupying one interval.

Zero faults means: every byte on disk matches the length and SHA-256 its record claims, every file is

against the decoded size for all 2,376 files, not by reading documentation.

### The confound, measured rather than asserted

Two facts fall out of that table and both are visible to a heuristic:

1. **Container.** Every one of the 1,653 fakes is PNG; 691 of the 723 reals are JPEG and not one real
   that is JPEG has a fake beside it. A rule as stupid as "it is a JPEG, so it is real" is right 2,344
   times out of 2,376 — **98.65 % measured** — which is the ceiling any heuristic here is working under
   and the reason `metadata`'s 0.0377 is an inverted container signal rather than a failure of the AUC.
2. **Size.** The fakes take four values (224², 256², 512², 1024²). The reals span **401 distinct sizes**,
   median larger edge 500 px, 77 % of them at or below 640 px, tail running to 3,840 px. Anything that
   reads a scale-dependent statistic is reading the index for most of the class even where container
   alone does not decide it.

Section 5 measures how much of each reported AUC those two facts account for.

`synthverify-thesis-v1`), so the header of the split file records `"seed": "20260929"` as a JSON string.

`sha256(f"{seed}|{sample_id}")` and both interpolate identically — but different file bytes, and so a
different digest. `sha256sum` of the file on disk equals the digest `score` printed and the
`split_digest` in the `eval` payload, which is the identity T59 asks for.

Refusals, with their reasons: the gate is per detector-cell, so the two thin commercial cells are
refused once under each of the four detectors that has any row for them — that is why the block prints
eight `below MIN_CELL_N=30` lines rather than two. `jpeg_history` is different in kind: it has no fake

and it is refused at the pooled row before any cell is drawn. A refusal prints no number, which is the
gate doing its job rather than a gap in it.

### Reading it before defending it

* Three of the four heuristics that report a number are **below chance** against these reals:
  `metadata` 0.0377, `ela` 0.3551, `frequency` 0.4352. An AUC under 0.5 is not a broken metric — it is
  the detector saying *the real images look more generated than the generated ones do*, which is what a
  detector trained on an artefact that the corpus's fakes happen not to have will do.
* `metadata` prints **the identical AUC and the identical interval in all six generator cells that
  report one**, and that is the whole story: its score does not vary with the generator, so every cell is
  measuring the same PNG-versus-JPEG decision. It is a container classifier wearing a forensics label.
* `noise` at 0.8585 [0.7920, 0.9063] is the only headline above chance. Section 5.1 shows why it cannot
  be reported as detection.

The finding, stated as the measurement: **`noise` separates two pools of real photographs from each
other at AUC 0.6998 [0.6197, 0.7693]**, and it separates DeciDiffusionV2's fakes from LCM's — same size,
same container, same source pool — at 0.3857. A detector that moves that much on differences that are
not generation is not measuring generation. **`frequency` separates the matched fake pair at 0.7454**
and `ela` at 0.1140, i.e. both are strongly generator-identifying rather than fake-detecting. That is
why the 0.8585 above is reported as *confounded* and not as evidence that the shipped heuristics work.

The authors of the corpus say the equivalent thing about their own field:

> we believe the classifiers, at least the ones that we have trained or benchmarked, still show far too
> high error rates to be used directly in the wild, and can lead to unwanted consequences (e.g. falsely
> accusing an author of creating fake images or allowing generated content to be certified as real).

## 6. What this establishes, and what it does not

Establishes, measured: the harness works end to end on bytes nobody here generated — 2,376 samples,
11,880 scored rows, zero unreadable, zero unscored, a split file whose digest is reproducible with
`sha256sum`, per-generator cells that clear `MIN_CELL_N` where the tranche was bought deep enough and
refuse where it was not, and refusals that carry reasons. It also
establishes that the reporting-side leak T58 closed was real: on this corpus an unfiltered read would
have mixed the 1,830 held-out rows with the 10,050 rows the heuristics had never been kept out of, and
printed one table for both.

Does not establish: that any shipped heuristic detects synthetic imagery. The five numbers above are
consistent with four of the five reading container, resize or source-index, and the fifth (`jpeg_history`)
cannot be evaluated on a corpus with this container split at all. The claim the thesis makes — evaluate
and fuse a learned detector — is not tested here; this tranche is the instrument check and the baseline
the learned detector has to beat *with these controls run against it too*.

Open, with the reason it is open:

* **A confound-matched tranche.** Same pixel size and same container on both sides. This tranche cannot
  supply one: all 1,653 fakes are PNG, at 224² (220), 256² (553), 512² (760) and 1024² (120), while of
  the 723 reals 691 are JPEG and the 32 that are PNG sit at none of those four sizes — measured, the only
  reals at 512² or 1024² are 3 JPEGs. So no subset of these bytes holds container and size equal on both
  sides, and **every fake-versus-real AUC above is an upper bound on detection ability, not an estimate
  of it.** Closing this needs a new fetch of matched reals, not a new analysis of the ones already here.
* **Calibration on this corpus.** ECE printed (0.18–0.72 across cells) with no threshold fitted on
  `calibration` yet, which is T57.
* **T60.** One score table per corpus avoids the bare-`sample_id` collision bug for now; it is not fixed.

## 7. Reproducing every number in this document

The corpus directory is gitignored, so this is the whole path from an empty machine, in order. Step 1
writes the images into `data/corpora/commfor/`; steps 2 and 4 are read-only checks; step 3 writes the
three artefacts (manifest, split file, score table) and refuses to rewrite any of them without
`--overwrite`.

```bash
# 1. Fetch the tranche. Operator-side: the product never reaches the network (FC-4).
./.venv/bin/python scripts/commfor_fetch.py --plan scripts/commfor_plan_v1.json   --out data/corpora/commfor --limit-mb 900
./.venv/bin/python scripts/commfor_fetch.py --plan scripts/commfor_plan_v1b.json  --out data/corpora/commfor --limit-mb 120
./.venv/bin/python scripts/commfor_fetch.py --plan scripts/commfor_plan_v1c.json  --out data/corpora/commfor --limit-mb 150
./.venv/bin/python scripts/commfor_fetch.py --plan scripts/commfor_plan_v1d.json  --out data/corpora/commfor --limit-mb 60

# 2. Prove what arrived: sizes, hashes, decodability, claimed versus measured format and size.
./.venv/bin/python scripts/commfor_check.py --root data/corpora/commfor

# 3. Write the manifest and the split assignment, and score the five image heuristics.
./.venv/bin/python -m synthverify.cli score \
  --scan-dir data/corpora/commfor --dataset commfor_eval_v1 \
  --generator dfgan:DFGAN --generator galip:GALIP --generator hourglass:Hourglass \
  --generator flux_dev:FLUX-dev --generator decidiffusionv2:DeciDiffusionV2 \
  --generator lcm_lora_sdv15:LCM_lora_sdv15 --generator midjourneyv5_2:MidjourneyV5_2 \
  --generator dalle3:Dalle3 --real-dir real \
  --manifest data/corpora/commfor/manifest-commfor_eval_v1.csv \
  --split-file data/corpora/commfor/split-commfor_eval_v1.json \
  --seed 20260929 \
  --table data/corpora/commfor/score-commfor_eval_v1.csv \
  --detectors ela,metadata,jpeg_history,frequency,noise

# 4. Re-run the check now that a manifest exists: this is the run whose table Section 3 prints,
#    because it also cross-checks every manifest row against the provenance line for the same file.
./.venv/bin/python scripts/commfor_check.py --root data/corpora/commfor \
  --manifest data/corpora/commfor/manifest-commfor_eval_v1.csv

# 5. The report. Exit 1 is the refusals, not a failure of the run.
./.venv/bin/python -m synthverify.cli eval \
  --table data/corpora/commfor/score-commfor_eval_v1.csv \
  --split-file data/corpora/commfor/split-commfor_eval_v1.json \
  --split held_out_test --by-generator

# 6. The same payload for a machine. --json appends the object after the table, so the file it
#    writes is not itself parseable JSON: take the payload from the first line that is a "{".
./.venv/bin/python -m synthverify.cli eval \
  --table data/corpora/commfor/score-commfor_eval_v1.csv \
  --split-file data/corpora/commfor/split-commfor_eval_v1.json \
  --split held_out_test --by-generator --json | sed -n '/^{/,$p' > eval-commfor_eval_v1.json

# 7. The null controls.
./.venv/bin/python scripts/commfor_nullcontrol.py \
  --table data/corpora/commfor/score-commfor_eval_v1.csv \
  --split-file data/corpora/commfor/split-commfor_eval_v1.json
```

`--detectors` names five of the eleven registered detectors, not all eleven: `score` resolves detectors
per sample by content-sniffed media type, and the registry raises on a requested detector that cannot
handle `image`. The six audio, video and text detectors are not applicable to this corpus.
